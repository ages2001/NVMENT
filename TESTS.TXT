NVMENT 3.0.0.0 - test results (QEMU 8.2, NVMe 1.4 controller "nvme")

Hibernation on Windows 2000 and XP x64 (2026-11-03)

- Display: S4 needs a driver on the display adapter. Windows 2000 with
  -vga cirrus: the in-box Cirrus Logic 5446 driver (display.inf),
  installed through SetupAPI. XP x64 with the std VGA: the in-box
  "Standard VGA Graphics Adapter" (display.inf, vgapnp.sys, which XP x64

  downloaded: the one free QEMU display driver source found
  (roytam1/vbemp, VBE miniport for NT 3.x) is x86 only and has no power
  management, so it would not have let S4 through either.
- Windows 2000 (256 MB, ACPI HAL, patched QEMU with AHCI link power
  management, NVMe HMB 8 MB and APST): system disk on AHCINT (ICH9
  port 0), 256 MB disks on AHCI port 1 (AHCINT), on the PIIX3 primary
  and secondary master (IDENT; the CD as secondary slave), an NVMe
  namespace (NVMENT) and an SD card on sdhci-pci (MMCSDNT). Power
  capabilities S3 1 S4 1, hibernation file reserved. bench.exe on the
  five data disks, hibernate, resume, bench again, hibernate, resume,
  bench again: all without errors; DRIVER.CAB from the CD and FC: equal
  afterwards; IDENTIFY through \\.\PhysicalDriveN still reached each
  disk (the SD card has none). After the second resume QEMU's log shows
  APST on, the HMB given again (2048 pages, every descriptor checked)
  and ALPE set on the AHCI ports; before the final power-off ALPE and
  ADSE were cleared (full power).
- XP x64 (512 MB, stock QEMU): system disk on IDENT (PIIX3 primary
  master), data disks on the primary slave and secondary master
  (IDENT), AHCI port 1 (AHCINT) and NVMe (NVMENT), the CD as secondary
  slave. S4 1, hibernation file reserved; the same two cycles with
  bench.exe before and after each: all without errors, then DRIVER.CAB
  and FC equal, IDENTIFY through each \\.\PhysicalDriveN.
- After a resume both systems lock the session; a power-off asked for by
  a program in that locked session (ExitWindowsEx returned success) did
  not power the machine off, it stayed at the logon screen. With the
  password on resume turned off (powercfg /globalpowerflag off /option
  resumepassword, XP x64) the same program powered off at once after a
  resume. Windows behaviour, not the drivers'.

SMART through the disk on XP x64 (added to 3.2.0.0, 2026-11-03)

- SMART through \\.\PhysicalDriveN (disk.sys) on XP x64: the request
  goes to the disk's PDO as IOCTL_SCSI_MINIPORT, which XP x64's ScsiPort
  (5.2.3790.1830) answers on a PDO with STATUS_INVALID_DEVICE_REQUEST
  (disassembly of its PDO device-control routine; only the adapter's
  device object takes it): smartt.exe reported ERROR_INVALID_FUNCTION on
  every disk of the driver, \\.\ScsiN: answered. The stock atapi.sys
  (not a ScsiPort miniport) answers on the same image. With the
  IRP_MJ_DEVICE_CONTROL front end the request is passed through the PDO
  as SRB_FUNCTION_IO_CONTROL (ScsiPort's PDO routine takes that function
  and fills in the disk's address).
- A first build without an MDL in that request stopped XP x64 with
  STOP D1 in ScsiPort (it maps the data of every request with
  DATA_IN/DATA_OUT through the IRP's MDL); with the MDL as below.
- XP x64 SP1 (5.2.3790.1830, ACPI HAL), an installed image moved to
  QEMU's PIIX3: system disk on the IDE primary master (IDENT), 256 MB
  disks as primary slave and secondary master, the XP x64 CD as
  secondary slave, a 256 MB disk on ICH9 AHCI port 1 (AHCINT), a 256 MB
  NVMe namespace (NVMENT); the three drivers installed with their INFs
  through SetupAPI. Release builds: bench.exe on the four data disks,
  DRIVER.CAB from the CD and FC: equal; IDENTIFY through
  SMART_RCV_DRIVE_DATA on \\.\PhysicalDrive0-4 returned each disk's own
  serial number (QM00001, PRISLAVE, SECMASTER, AHCIP1, NVME1), SMART READ
  DATA answered on each; 32-bit and 64-bit test programs; shutdown
  powered off.
- Windows 2000 (regression, release builds): IDENTIFY through
  \\.\PhysicalDriveN returned the serial of each disk of the driver
  (the 2000 ScsiPort passed these on before as well); bench, DRIVER.CAB
  and FC, SMART, hot plug and card change as before.

Host Memory Buffer, APST by default (added to 3.2.0.0, 2026-11-02)

QEMU 8.2's NVMe controller has neither; it was patched for these runs:
with QEMU_NVME_HMB=<KB> it reports HMPRE (that size) and HMMIN (half of
it) and takes Set Features 0Dh, checking every descriptor (page aligned,
the sizes adding up to HSIZE) by writing and reading back 16 bytes at
both ends of every piece; with QEMU_NVME_APST=1 it reports APSTA and two
non-operational power states (PS1: 1 ms entry / 2 ms exit, PS2: 5 ms /
20 ms) and takes Set Features 0Ch. Each accepted command is logged.
- Windows 2000 (256 MB RAM), debug build, no DriverParameters:
  - controller asking for 32 MB (16 MB minimum): "limit 16344 KB: not
    given" (1/16 of the RAM is less than the minimum), no Set Features
    0Dh, the controller runs without a buffer.
  - controller asking for 8 MB: "8192 KB in 2 piece(s) ... on"; QEMU:
    2048 pages, 2 descriptors, all checked, accepted.
  - "APST on"; QEMU: the table entry for PS0 goes to PS1 after 150 ms.
  - bench.exe on the NVMe disk: no errors; nvmecfg.exe lists the
    controller and its namespace.
  - POWER_DOWN and POWER_UP IOCTLs twice (mpctl.exe): QEMU shows APST
    off before each shutdown notification, the buffer dropped by the
    controller reset, and APST and the buffer given again (the same
    descriptors) when the controller is set up again; bench afterwards
    without errors.
- Release build of this round, the patched QEMU: the same sequence in
  QEMU's log (buffer given, APST on; APST off and the buffer dropped at
  each POWER_DOWN; both given again at POWER_UP), both bench runs
  without errors. On the unpatched QEMU (no HMPRE, no APSTA): bench and
  the port program as before.
- Not tested: a real DRAM-less SSD; NT 3.1-4.0 (MmQuerySystemSize path)
  and XP x64 (ZwQuerySystemInformation with the 64-bit structure size)
  were not run with a controller that asks for a buffer.

nvme2k 1.5.0.0 - test results (QEMU 8.2, NVMe 1.4 controller "nvme")

Builds tested
- bin\NT\nvme2k.sys (NT 3.1 - 4.0) was built from these sources with
  i686 MinGW (GCC 13, -mrtd = stdcall like the DDK's /Gz) against an
  import library made from NT 3.1's own SCSIPORT.SYS; it imports nothing
  NT 3.1 lacks.
- bin\2KXP\i386 and bin\2KXP\amd64\nvme2k.sys were built with MinGW
  (i686 / x86_64) against import libraries made from Windows 2000's and
  XP x64's SCSIPORT.SYS and NTOSKRNL.EXE.
- The DDK projects (nt4, w2k, WDM) build the same sources; they were not
  run here.

Test setup
- QEMU 8.2.2. Two namespaces on one controller: NSID 1 with 512-byte
  and NSID 2 with 4096-byte LBAs (FAT volumes on both).
- Test environment only: SeaBIOS hangs NTDETECT when it maps a 4 KB
  namespace, so for the data-disk tests a patched QEMU hid the
  namespaces until the second controller enable (the driver's).
  Booting from NVMe used an unpatched setup (one 512-byte namespace).
- Load test: a CrystalDiskMark-like tool (no buffering, write-through,
  overlapped I/O): 1 MB sequential write/read, 512 KB and 4 KB random
  write/read, 4 KB at queue depth 32, then a full re-read. Every sector
  carries its own number and a generation tag, so a misplaced, stale or
  lost write is detected.
- Feature test (nvtest, SCSI pass-through and miniport IOCTLs, on both
  namespaces): INQUIRY, READ CAPACITY(10/16) with LBPME, READ(10/12),
  FUA, read past the end (ILLEGAL REQUEST / 21h), VERIFY(10/16),
  SYNCHRONIZE CACHE(10/16), REPORT LUNS (2 LUNs), MODE SENSE(10)
  caching page (WCE, DPOFUA), MODE SELECT(10) write cache off -> MODE
  SENSE shows it off -> on again, VPD B0 (block limits), START STOP UNIT
  stop -> READ -> start, SMART through "SCSIDISK" (VERSION, IDENTIFY,
  READ ATTRIBUTES), NVME2KDB QUERY_INFO / POWER_DOWN / read wakes the
  controller / POWER_DOWN / POWER_UP / read.

Windows NT 3.1 (SP0, Standard HAL, system disk on AHCI with AHCINT)
- Driver load with NT 3.1's ScsiPort: the full-size structure is
  refused (C0000059), the driver retries with the 40h-byte layout on the
  ISA bus and finds the controller through ports CF8h/CFCh.
- Fast Polling (default) and IRQ=1 (INTx, up to 16 commands queued):
  feature test on both namespaces, load test on the 512-byte FAT volume,
  chkdsk clean. NT 3.1's FAT driver does not mount the 4 KB volume (the
  same as on AHCI); the 4 KB namespace works as a disk (feature test).
- Installed with oemsetup.inf (Windows NT Setup - Add/Remove SCSI
  Adapters - Other): miniport as boot driver, class driver key set from
  Start = 3 to 0.
- The miniport has to be a boot driver: with Start = 1 scsidisk (a boot
  driver) has already looked for disks and the NVMe disks do not appear.
- Found with the INF-installed driver (Tag 33): it loaded before AHCINT
  (set up untagged by text-mode setup), the NVMe disks became the first
  disks and boot.ini's multi() path pointed at the wrong disk - STOP 6B.
  oemsetup.inf now sets no Tag; without it the boot and all tests pass.
  On NT 4.0 the service gets a Tag from NT 4.0's own registry.inf
  (34, after AHCINT's 33); the system boots and the tests pass.

Windows NT 4.0 (SP6, system disk on AHCI with AHCINT)
- UP HAL: feature test, load test and CRC32 file lists on both volumes,
  chkdsk - no errors.
- MPS HAL with 2 CPUs: the same; up to 15 commands queued. 4 KB random
  I/O is slow on this QEMU setup with the MPS HAL - the same with AHCINT.
- Installed with oemsetup.inf (Control Panel - SCSI Adapters - Have
  Disk) from a floppy: boot driver, class driver key set from Start = 3
  to 0, feature test after the reboot.
- NT 4.0 and Windows 2000 return a failed pass-through command as an I/O
  error (1117) instead of the CHECK CONDITION status; the driver's
  sense data are not visible to the tool there.

Windows 2000 (5.0.2195, UP ACPI HAL)
- Installed through nvme2k.inf (UpdateDriverForPlugAndPlayDevices).
- Data disks: feature test and load test on both namespaces, CRC32 list,
  chkdsk - no errors.
- Hibernation with the NVMe disks as data disks (system disk on AHCI):
  ScsiStopAdapter, hibernation, resume through ScsiRestartAdapter; after
  resume the feature test, a load test on the NVMe volume and the CRC32
  lists of four other volumes, chkdsk - no errors.
- System disk on NVMe (boot through SeaBIOS, multi() path):
  boot, load test, and hibernation. The dump stack loads a second
  instance in Fast Polling, which writes the hibernation file to the
  NVMe disk; resume, CRC32 lists of four data volumes, chkdsk - no
  errors. This run found the queue alignment problem fixed in 1.5.0.0:
  the dump stack's DMA buffer started 20h bytes into a page, the admin
  queues were not page-aligned and the controller stopped with CFS, so
  hibernation was refused.
- S3 (standby) does not come back under QEMU/SeaBIOS in this setup, also
  without NVMe (see the AHCINT tests); the driver's stop was logged.

Windows XP x64 (5.2.3790), text-mode setup with F6 (floppy_amd64)
- NVMe disk as the only hard disk, setup CD on IDE: driver from the F6

Controllers without a disk

  namespaces: the driver answered REPORT LUNS / INQUIRY for LUN 0 with a

  driver retried forever. Now LunCount = 0 presents no LUN at all

  controller without namespaces next to the system disk (Windows 2000
  with an empty AHCI HBA too: desktop in 55 s), and with the driver
  installed but no controller present (service fails with C00000C0, no
  hang). The same check was done with AHCINT (see its TESTS.TXT).

QEMU q35 machine (ICH9 AHCI, PCIe root complex), Windows NT 3.1

Shutdown on Windows XP x64 (3.1.0.0)
Looking into a hang at shutdown reported on XP x64 with AHCINT 1.5.0.0
(XP x86 and 2000 not affected on the same machine, as reported). Not
reproduced in QEMU in any of these runs, so the change in this release
is the one x64-only difference found in the code, not a confirmed fix.
- XP x64 SP1, F6 installation with all four drivers on one floppy
  (system disk on AHCI through AHCINT, an NVMe disk through NVMENT, an
  SD card on a PCI SDHCI through MMCSDNT, PIIX3 disk and CD through
  IDENT), GUI-mode setup at Regional Options, debug builds: shutdown
  from the setup command prompt through NtShutdownSystem (power off) and
  restart: powered off after 5-10 s, restart back at the driver load
  after 15 s. Repeated with 4 CPUs, with 2 GB of the 3 GB RAM above
  4 GB, with a SATA DVD on an AHCI port, with a PCI power management
  capability added to QEMU's AHCI (which has none; Windows did not take
  the HBA to D3 at shutdown), and with a QEMU patch that delays every
  NCQ command after STANDBY IMMEDIATE by 8 s (a disk spinning up): no
  hang. A traced build showed the order on XP x64: the last writes and
  SYNCHRONIZE CACHE / FLUSH, then SRB_FUNCTION_SHUTDOWN (flush, standby),
  and no request after it.
- Windows 2000 SP4, system on AHCI (AHCINT), NVMe data disk (NVMENT),
  PIIX3 disk (IDENT): a file copy and a registry change, then shutdown
  through ExitWindowsEx: powered off, also with the spin-up delay.
